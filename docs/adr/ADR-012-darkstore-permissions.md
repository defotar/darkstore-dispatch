# ADR-012. Права по даркстору

**Статус:** принято

## Контекст

АС должна знать, какой пользователь прислал команду и к какому даркстору он относится.

**Вопрос:** Как АС узнаёт пользователя и его даркстор

**Основание:** D04-S04-NFR004; D05-S02-FR044; интеграция И-09

## Варианты

| Вариант | Достоинства | Недостатки |
|---|---|---|
| Токен сервера учётных записей сети и Spring Security в ОФ-2 | Известны пользователь и его даркстор; подпись токена проверяется открытым ключом без обращения к серверу | Нужен атрибут даркстора в токене |
| Только сертификаты систем | Простота | Известна система-отправитель, но не куратор |
| Ключи API | Самый простой вариант | Не известен пользователь, риск утечки ключа |
| Собственный справочник пользователей в АС | Независимость от сети | АС хранит пароли и дублирует учётные записи сети |

## Критерии

К1 — известен конкретный пользователь; К2 — известен его даркстор; К3 — АС не хранит пароли. Сертификаты и ключи API не выполняют К1 и К2, собственный справочник — К3

## Решение

Токены сервера учётных записей сети, проверка в ОФ-2 средствами Spring Security; системы дополнительно предъявляют сертификат.

**Цена решения:** зависимость от атрибута даркстора в токене

## Как проверить

Тестовый токен куратора; команда по чужому даркстору отклоняется
